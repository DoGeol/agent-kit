# crew 규칙

`crew <build|check|plan> <직군>[:<스택>][,<직군>[:<스택>]] <요청 또는 spec 경로>`. 본 세션이 맡기는 쪽(진행자)이고, 역할은 서브에이전트가 맡는다. 서브에이전트를 못 띄우는 도구에서는 본 세션이 역할 파일을 읽고 그 역할로 순서대로 한다.

## 1. 인자

- 직군: `frontend` `backend` `qa` `designer` `reviewer` `security`. 없으면 요청 내용과 레포 파일로 추천을 1번에 놓고 `ask.md` 형식으로 묻는다. 둘 이상은 쉼표로.
- 스택: 없으면 직군 + 레포 파일로 판단하고 첫 줄에 표시한다(`pyproject.toml` python, `build.gradle`·`pom.xml` java, `package.json`에 `react`면 frontend는 react, 그 밖 node). 모노레포처럼 섞이면 묻는다.
- 요청: 문장이거나 spec 경로. spec이면 `## 기능`의 직군 표시로 직군을 고를 수 있다.
- 첫 줄: `재료: crew.md · dispatching-parallel-agents(병렬일 때) · 역할 backend:python`.

## 2. 브리핑 (모든 역할 공통)

받는 쪽은 빈 기억이다. **절대 경로만** 넘기고 파일 내용은 복사하지 않는다. 이 Skill 폴더의 절대 경로(이 파일이 있는 폴더)를 `<KIT>`라고 할 때:

```
kit-brief: <직군>[:<스택>]
읽을 것: <spec 절대 경로>, <contract.md 절대 경로 (있으면)>, <레포 AGENTS.md·CLAUDE.md (있으면)>
역할: <KIT>/_roles/<직군>.md
형식: <KIT>/_roles/review-format.md            ← check일 때
스택: <KIT>/_stacks/<스택>/STACK.md            ← 파일이 있을 때
참고: <KIT>/_roles/<직군>/reference.md         ← 해당 상황일 때
범위: <기능 ID와 서브태스크>, <고쳐도 되는 경로>
산출: <레포>/.kit/<slug>/<종류>-<직군>.md       ← report-backend.md, review-security.md
작업: <요청 문장 한두 줄>
```

- 첫 줄 `kit-brief:`가 없으면 생성된 에이전트는 일하지 않는다. 반드시 첫 줄.
- 띄우기 전에 브리핑 전문을 `.kit/<slug>/brief-<직군>.md`에 그대로 저장한다. 넘기는 브리핑은 이 파일 내용으로 시작해야 한다(뒤에 덧붙이는 것은 괜찮다). 아니면 Claude Code에서는 훅(`hooks/agent-guard.py`)이 호출을 막고(사용자가 이 세션에서 crew 명령을 친 뒤 저장한 파일만 인정한다), 다른 도구에서는 에이전트가 일하지 않는다. 같은 직군을 다시 띄우면 파일을 새 브리핑으로 덮어쓴다. 같은 직군을 동시에 둘 이상 띄우면 `brief-<직군>-2.md`처럼 번호를 붙여 따로 저장한다. Claude Code의 훅은 사용자가 crew 명령에 적은 직군만 통과시킨다. 진행 중에 다른 직군이 필요하면 사용자에게 묻고, 사용자가 그 직군으로 crew 명령을 다시 치게 한다.
- `.kit/`는 레포의 `.git/info/exclude`에 한 줄 넣어 커밋되지 않게 한다(없으면 추가).
- 서브에이전트가 있는 도구: 직군 이름의 에이전트(`kit:<직군>` 또는 `<직군>`)가 있으면 그것으로, 없으면 일반 에이전트에 위 브리핑 그대로. review 역할은 파일을 고치지 않는 설정으로.
- 모델: 생성된 에이전트는 세션 모델을 물려받는다. `_roles/<직군>.md`에 `model:`이 있는 직군(designer·reviewer·security는 `opus`)은 도구가 호출마다 모델을 고를 수 있으면 그 모델로 띄운다.

## 3. build

1. 직군 하나: 브리핑 → 띄움 → 끝나면 산출 파일을 읽고 **3줄로 보여 준다**(바뀐 파일, 테스트 결과, 남은 것) → "다음: `/check`" 한 줄.
2. 직군 둘 이상: `ask.md` 형식으로 묻는다 — 병렬(계약 먼저, 기능이 서로 독립일 때 추천) / 순차(계약이 흔들릴 때) / 하나로(변경이 작을 때). 서브에이전트가 없는 도구에서는 병렬을 보이지 않는다.
3. 병렬이면 (`dispatching-parallel-agents`의 원칙: 서로 독립인 일만, 겹치는 파일 없음, 결과는 진행자가 합친다):
   1. 본 세션이 spec에서 맞닿는 부분만 `contract.md`로 뽑는다: 엔드포인트, 요청·응답 모양, 오류 코드, 이벤트. 애매하면 여기서 묻는다. 경로는 `.kit/<slug>/contract.md`.
   2. 직군마다 브리핑을 쓰고 **한 번에 동시에** 띄운다. 범위에 서로 안 겹치는 경로를 적는다. 도구가 에이전트마다 작업 폴더(워크트리)를 줄 수 있으면 그렇게 한다. frontend는 계약대로 mock을 먼저 세운다. 둘 다 계약 테스트를 쓴다.
   3. 끝날 때마다 산출을 읽고 3줄로 보여 준다. `.kit/<slug>/contract-changes.md`에 줄이 생기면 본 세션이 판단해 `contract.md`를 고치고 상대에게 알린다(가능한 도구에서는 메시지로, 아니면 다음 브리핑에). 같은 건으로 3회 넘으면 사용자에게 카드.
   4. 모두 끝나면 합친다(워크트리면 머지), 계약 테스트와 레포 테스트를 돌린다, 결과를 보여 준다. "다음: `/check`".
4. 순차면 backend → frontend 순으로 1번을 반복하되 앞 결과 경로를 다음 브리핑 `읽을 것:`에 넣는다.
5. 하나로면 직군 하나 브리핑에 범위를 전부 넣는다.

## 4. check

직군마다 브리핑(`형식:` 포함, `산출: <레포>/.kit/<slug>/review-<직군>.md`)을 동시에 띄운다. 끝나면 파일마다 `VERDICT`와 지적 수를 보여 주고, 지적은 심각도 순으로 합쳐 5개까지 보인다. 끝에 "고치려면 `/dev 지적 1·3번 반영`". `/check`와 다른 점: 여러 관점을 동시에, 산출이 파일로 남는다.

## 5. plan

spec을 작업 단위로 쪼갠다. 표: ID, 직군, 하는 일 한 줄, 기대는 ID, 검증 명령, 크기(S/M/L). 서로 독립인 작업을 묶어 "동시에 할 수 있는 묶음"을 표시한다. `docs/specs/<slug>-plan.md`에 쓴다. 끝에 "시작하려면 `crew build <직군> <spec 경로>의 <ID>`".

## 6. 진행자가 지키는 것

- 끝났다는 보고를 믿지 않는다. 산출 파일과 `git diff`·테스트 결과를 직접 본다. 산출이 없으면 "없음"으로 보고하고 다시 띄울지 묻는다.
- 같은 역할이 같은 작업에서 2회 실패하면 멈추고 사용자에게 상황과 선택지를 카드로.
- 기능 3개·반나절을 넘는 일은 받지 않는다. "`/spec`으로 쪼개서 기능마다 `crew build`" 한 줄.
- 직군은 한 번에 둘까지 병렬. 셋 이상은 순차.
- 본 세션은 레포 코드를 고치지 않는다(합치기와 계약 파일만).
