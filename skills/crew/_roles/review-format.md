# 리뷰 공통 형식

review 역할(reviewer, security, designer)과 `/check`, 그리고 build 역할이 리뷰를 맡았을 때 같이 쓴다. 역할 파일의 "리뷰에서 보는 것"과 함께 받는다.

## 읽기

- 브리핑에 적힌 경로만 읽는다. 내용을 추측하거나 다른 작업의 파일을 뒤지지 않는다. 읽지 못한 파일은 "읽지 못함"으로 적는다.
- 대상이 건드리는 코드는 검색해서 필요한 만큼만 읽는다.
- 셸을 쓰면 `git diff`·`git log`·`git show`만 쓰고 `>`, `<`, `|`, `;`를 넣지 않는다 (파일이 생기거나 다른 명령이 돈다).

## 리뷰 파일

브리핑의 산출 경로 한 파일. 산출 경로가 없으면 답으로 돌려준다.

- 첫 줄 `VERDICT: pass` 또는 `VERDICT: issues`. 지적이 하나라도 있으면 `issues`.
- 지적은 심각도 순 상위 5개까지 (브리핑이 "넓게"라고 하면 10개). 항목마다 `심각도(high|medium|low)`, `위치(spec 절 또는 파일:줄)`, `문제`, `근거(코드 경로·사실·재현 조건)`, `제안`, `확신도`.
- 범위는 정확성과 요구사항 빠짐만. 취향(이름, 스타일, "나라면 이렇게")은 쓰지 않는다.
- 지적이 없으면 `VERDICT: pass` 아래 "확인한 범위"를 세 줄 이내로.

## 반박에 답할 때 (브리핑이 "토론 답"일 때)

누군가 내 지적을 반박하거나 새 지적을 냈을 때 다시 불린다. 토론 파일과 대상을 다시 읽고 브리핑의 답 파일 하나에만 쓴다.

- 내 번호의 줄과 내 분야의 새 지적마다 한 줄: `<번호>: 수용 | 반론 — 근거(위치·재현 조건)`.
- 반박이 맞으면 수용한다. 반론은 새 근거가 있을 때만.

## 끝내기

반환은 3줄: 쓴 파일 경로 / VERDICT와 지적 수(토론 답이면 수용·반론 수) / 가장 심각한 지적 한 줄 또는 "없음". 파일 내용을 옮겨 적지 않는다.

## 하지 않는 것

- 코드·spec 수정. 쓰기는 리뷰 파일과 답 파일에만.
- 다른 에이전트 부르기, 다른 역할에게 직접 묻기 (맡긴 쪽이 전한다).
- 브리핑에 없는 파일 내용을 가정하기.
