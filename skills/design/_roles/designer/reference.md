# designer 참고: 디자인 원칙 문서

[← designer 역할](../designer.md). 브리핑에 `참고:`로 넘길 때만 읽는다. 원칙 문서는 `stacks/design/team.md`에 둔다(없으면 그 자리에 만든다).

## 디자인 원칙 초안 만들기
원칙 문서가 없는 프로젝트에서 처음 설계할 때, 또는 사용자가 원칙 정리를 요청할 때.
- 기존 문서(디자인 정책 문서, 브랜드 문서)가 있으면 새로 만들지 않고 그 문서에 어떻게 더할지 묻는다.
- 화면이 있으면 먼저 목록을 만든다: 같은 역할의 요소(버튼, 제목, 빈 상태, 날짜 표시)를 모아 쓰인 변형을 센다. 반복되는 선택은 관찰된 기본값이고, 한두 곳만 다른 것은 의도인지 우연인지 질문으로 남긴다.
- 관찰된 기본값을 설명하는 "A를 B보다 우선한다" 문장으로 원칙 3~5개를 쓴다. 반대 문장이 다른 제품에서 맞지 않으면 원칙에서 뺀다.
- 원칙마다 근거를 화면 경로나 코드 위치로 단다. 근거가 없으면 지어내지 않고 질문으로 남긴다.
- 문서 전체와 원칙 모두 `상태: draft`로 둔다. 원칙 이름과 순서는 추천안과 함께 선택지로 사용자에게 묻는다. 사용자가 승인한 원칙만 `accepted`가 된다.

## 디자인 원칙 바꾸기
설계 중 원칙으로 설명되지 않는 결정이 필요하거나, 원칙끼리 부딪힐 때.
- 결정을 원칙에 맞게 고칠 수 있으면 고친다. 아니면 원칙 변경을 제안한다. 문서를 직접 바꾸지 않는다.
- 제안은 결정 기록 한 줄(`proposed`)과 바꿀 문장으로 낸다. 근거: 이 변경이 필요한 화면이 둘 이상인지, 기존 원칙과 겹치지 않는지, 대체라면 왜 더 나은지.
- 승인되면 새 기록은 `accepted`, 대체된 기록은 지우지 않고 `superseded by D-00x`로 둔다. 상단 검토 날짜를 고친다.
- 최근 설계 문서에서 한 번도 인용되지 않은 원칙이 있으면 다시 쓰거나 지우자고 제안한다.
