# 리뷰 규칙

`/check`가 따르는 절차. 읽기 전용. 파일을 고치지 않는다.

## 1. 대상과 관점

- 직군이 없으면 `reviewer`. `security`·`qa`·`designer`·`frontend`·`backend`를 적으면 그 역할 파일의 "리뷰에서 보는 것"으로 본다. `design`은 `designer`로.
- 대상이 없으면 현재 변경: 작업 트리·스테이지 diff. 비어 있으면 기준 브랜치와 비교(`git diff <기준>...HEAD`, 기준은 `main`·`master`·`develop` 중 있는 것). 그래도 비어 있으면 무엇을 볼지 묻는다. 대상이 브랜치·커밋·경로·PR 번호면 그것.
- 스택이 없으면 레포 파일로 판단한다. 맞는 `_stacks/<스택>.md`가 있으면 그 규칙과도 대조한다.
- 첫 줄에 적는다: `재료: reviewer · 5관점 · 스택 react · 대상 git diff main...HEAD (12 files)`.

## 2. 읽기

- diff 전체를 읽는다. 바뀐 함수의 호출자를 검색해 확인한다. 필요한 파일은 전문을 읽는다.
- 셸은 `git diff`·`git log`·`git show`·검색만. 리다이렉션·파이프를 쓰지 않는다.
- `code-reviewer`의 5관점 순서로 훑는다: 정확성 → 가독성 → 구조 → 보안 → 성능. 보안 관점이거나 `security`면 `security-auditor`의 목록(입력, 인증·권한, 비밀값, 의존성, 데이터 노출)으로 한 번 더.
- ponytail이 설치돼 있고 Skill 목록에 `ponytail-review`가 있으면 그것도 읽어 "줄일 것" 관점을 더한다.

## 3. 쓰기

`review-format.md` 형식. 지적마다 심각도·위치(파일:줄)·실패 상황(이 입력·순서면 이렇게 틀린다)·근거·제안·확신도. 확신도 80 미만은 보류 목록에. 취향·문체는 넣지 않는다. 바뀌지 않은 줄의 기존 문제와 린터가 잡을 것은 넣지 않는다.

산출 경로를 받았으면 그 파일에, 아니면 답으로. 구성:

```
VERDICT: pass | issues
spec 준수: 지킴 | 어김(항목) | spec 없음
## 지적 (심각도 순, 5개까지)
1. [high] 파일:줄 — 문제. 실패 상황: … 근거: … 제안: … (확신 90)
## 보류
## 확인 못 한 범위
병합 가능? 예 | 아니오 | 수정 후
```

끝에 한 줄: "고치려면 `/dev 지적 1·3번 반영`".

## 하지 않는 것

- 파일 수정, 커밋. 리뷰 중 고치고 싶은 게 보여도 지적으로만.
- 범위 밖 리팩터링 제안.
- 결과를 부드럽게 쓰기. 지적이 없으면 `VERDICT: pass`와 확인한 범위 세 줄.
