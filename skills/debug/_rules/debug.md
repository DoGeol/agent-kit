# 디버깅 규칙

`/debug <증상>`이 따르는 절차. 뼈대는 superpowers `systematic-debugging`(4단계: 원인 조사 → 패턴 분석 → 가설·실험 → 구현). 여기 적은 것은 덮어쓰기와 앞에 붙이는 단계다.

## 0. 비밀값 가리기

명령·출력·로그를 보일 때 토큰·키·개인정보는 `<REDACTED>`로. 재현 명령은 환경변수를 읽게 만들어 값이 대화에 남지 않게 한다.

## 1. 되풀이할 수 있는 신호부터 (가장 중요)

고치기 전에 **이 버그에만 빨간불이 켜지는** 확인 수단을 만든다. 이게 있으면 나머지는 기계적이고, 없으면 추측이다. 순서대로 시도:

1. 실패하는 테스트(단위 → 통합 → e2e 중 버그에 닿는 가장 낮은 층)
2. 실행 중인 서버에 보내는 요청 스크립트
3. 고정 입력으로 CLI를 돌려 출력 비교
4. 브라우저 자동화 스크립트로 화면·콘솔·네트워크 확인
5. 실제 요청·이벤트를 파일로 잡아 두고 그 코드 경로에만 다시 흘리기

만들기 어려워도 포기하지 않는다. 정말 안 되면 왜 안 되는지 적고 사용자에게 묻는다. 신호가 생기면 첫 줄에 적는다: `신호: tests/test_cancel.py::test_refund_twice (실패)`.

## 2. systematic-debugging의 4단계

`_vendor/systematic-debugging.md`를 따른다. 덮어쓰기:

- 1단계(원인 조사)에서 호출자를 전부 찾는다. 증상이 보인 곳만 고치지 않는다.
- 3단계(가설)는 한 번에 하나. 가설 → 실험(1절의 신호로) → 결과를 한 줄씩 남긴다.
- 같은 가설을 바꿔 가며 3번 고쳐도 안 되면 멈춘다. 알게 된 것과 남은 가설을 적고 `ask.md` 형식으로 묻는다(계속 / 범위 넓히기 / 되돌리기).
- 원인을 못 찾은 채 "일단 이렇게 하면 됨" 식 우회는 하지 않는다. 우회가 필요하면 그렇다고 적고 사용자가 정한다.

## 3. 고친 뒤

- 1절의 신호가 초록으로 바뀐 것을 실제로 돌려 보인다. 회귀 테스트로 남긴다.
- 같은 원인을 쓰는 다른 곳이 있으면 목록으로 보고한다(고치는 건 요청 범위 안에서만).
- 보고 3줄: 원인(파일:줄, 한 문장), 고친 것, 남긴 테스트.

## 하지 않는 것

- 신호 없이 코드 고치기. 증상만 가리기(try/except 추가, 기본값 대체).
- 요청 밖 리팩터링.
- 커밋(요청했을 때만).
