# /spec

요청: 명령 뒤에 적힌 문장. 비었으면 "무엇을 만들지 한두 문장으로 적어 주세요"로 멈춘다.

| 재료 | 쓰는 곳 |
|---|---|
| `_rules/spec.md` | 전체 절차 (뼈대) |
| `_rules/ask.md` | 질문 형식: 카드 있으면 카드, 추천 첫 번째, 4개까지 |
| `_vendor/grilling.md` | 1단계: 결정 나무, 한 라운드에 지금 물을 수 있는 것 전부 |
| `_vendor/to-spec.md` | 3단계: `<spec-template>` 절만. 이슈 트래커·라벨 부분은 쓰지 않는다 |
| ponytail (설치돼 있으면) | 4단계 깎기에서만. 1~3단계에는 쓰지 않는다 |

## 절차

1. 첫 줄에 재료를 적는다: `재료: grilling(질문) · to-spec 틀(초안) · 세 질문(깎기)`.
2. `_rules/spec.md`를 읽고 1→5 순서대로 한다. 질문은 `_rules/ask.md` 형식으로, 한국어로.
3. `_vendor/grilling.md`의 질문 방식을 따르되 형식은 `ask.md`가 이긴다(❓·➡️ 대신 번호 목록 또는 카드). 사실은 사용자에게 묻지 않고 레포에서 찾는다.
4. 초안은 `_vendor/to-spec.md`의 템플릿 절 순서를 `_rules/spec.md` 3절의 한국어 절 이름으로 쓴다.
5. 끝에 한 줄: 경로, 기능 수, 열린 질문 수. 그리고 "구현은 `/dev docs/specs/<slug>.md의 F1`처럼 기능 단위로". 명령 이름은 사용자가 이 명령을 부른 형식을 따른다(`/kit:dev`·`$dev`·`/dev`).

## 하지 않는 것

- 코드 수정, 커밋.
- 짧은 말투. spec은 사람이 읽는 문서다.
- 질문 없이 바로 spec 쓰기(요청이 아무리 명확해 보여도 최소 한 라운드는 확인한다. 정말 명확하면 "확인 1개"로 짧게).
