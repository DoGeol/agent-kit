# 개발 규칙

`/dev`가 따르는 규칙. ponytail·caveman이 설치돼 있으면 그쪽이 더 자세하고, 없으면 이것만으로 간다.

## 고치기 전에

- 바뀔 곳을 전부 찾는다: 호출자, 테스트, 설정, 내보내기. 그게 범위다. 요청 밖 기능은 범위가 아니다.
- 가정이 있으면 한 줄로 말한다. 해석이 둘이면 둘 다 보이고 고르게 한다. 더 단순한 길이 있으면 먼저 말한다.
- 레포 규칙(`AGENTS.md`, `CLAUDE.md`, lint 설정)과 테스트 명령을 먼저 찾는다.

## 테스트 먼저

- 핵심 경우만 1~3개: 정상 1, 실제로 일어날 경계·오류 1~2.
- 동작(입력 → 결과)을 검증한다. 구현 세부에 묶지 않는다.
- 테스트를 통과시키려고 입력을 하드코딩하거나 테스트 전용 분기를 만들지 않는다. 테스트가 틀렸으면 테스트를 고친다.

## 최소 변경

- 요청 밖 기능, 옵션, 추상화, 설정, "나중을 위한" 코드를 넣지 않는다.
- 순서: 레포에 이미 있는 것 → 표준 라이브러리·플랫폼 기능 → 설치된 의존성. 몇 줄 때문에 의존성을 추가하지 않는다.
- 옮기거나 합친 코드는 오류 처리와 검증을 그대로 지닌다. 경계의 검증, 데이터 손실을 막는 오류 처리, 보안, 접근성은 줄이지 않는다.
- 버그면 고치기 전에 그 함수의 호출자를 모두 찾고, 공유 코드에서 원인을 한 번만 고친다.
- 주석은 코드가 말하지 못하는 "왜"만 한 줄.

## 끝났다고 하기 전에

- 테스트·타입체크·lint 명령을 **실제로 돌리고** 결과를 보인다. 안 돌렸으면 "안 돌렸다"고 쓴다.
- "될 것이다"는 결과가 아니다. 명령 출력과 종료 코드가 결과다.

## 답하는 법

- 결론 먼저, 꾸밈 없이. 기술 사실은 빠뜨리지 않는다.
- 보안 경고, 되돌릴 수 없는 일, 사용자가 혼란스러워 보일 때는 온전한 문장으로.
- **세션 밖으로 나가는 글은 일반 문장**: 커밋 메시지, PR 본문, 이슈, 슬랙. 짧은 말투를 쓰지 않는다.
- 한국어 커밋 메시지: "~을 수행함/진행함/실시함" 같은 사무적 동사 대신 동사 그대로("로그인 재시도 추가"). type/scope 접두사와 파일·함수명은 그대로.

## 범위

`/dev`를 친 작업이 이어지는 동안(테스트 → 구현 → 수정의 후속 턴) 이 규칙을 유지한다. 사용자가 다른 주제를 꺼내거나 `/write`·`/spec`을 치면 풀린다.
