# 화면 설계 규칙

`/design <화면>`이 따르는 절차. 코드는 고치지 않는다. 산출은 설계 문서 한 장. 짧은 말투를 쓰지 않는다.

## 1. 대상

화면 하나. "대시보드 전체"처럼 넓으면 가장 효과가 큰 화면 하나로 좁히고 나머지는 다음 호출로 미룬다. 대상이 없으면 묻는다.

## 2. 바닥 확인 (묻지 않고 찾는다)

- 스택과 스타일 체계, 토큰(색·간격·글자·둥글기·모션), 재사용할 컴포넌트와 상태 컴포넌트(빈·로딩·오류).
- 비슷한 기존 화면: 같은 역할의 요소가 어떻게 생겼나. 그것이 관찰된 기본값이다.
- `design/team.md`(디자인 원칙)가 채워져 있으면 그것이 우선. 결정마다 원칙 ID를 적는다. 비어 있으면 `design/STACK.md`의 일반 기준.
- 제품 성격(일상 도구인가, 소비자 앱인가). 이것이 얼마나 과감할 수 있는지의 상한이다.

## 3. 질문 라운드

`grilling` 방식(지금 물을 수 있는 것을 한 라운드에 전부), `ask.md` 형식(카드, 추천 첫 번째, 4개까지). 디자인 질문은 이 순서로 열린다:

1. **목적**: 이 화면에서 사용자가 끝내려는 일 하나. 성공은 무엇인가.
2. **독자**: 누가, 얼마나 자주, 어떤 기기에서. 하루 100번 보는 화면과 한 달에 한 번 보는 화면은 다르다.
3. **내용 우선순위**: 반드시 한눈에 보일 것 하나, 두 번째, 접어도 되는 것. 데이터 양(건수, 열 수)과 비교 빈도.
4. **제약**: 기존 토큰·컴포넌트 안에서 하나, 새 요소가 필요한가. 좁은 화면 필수인가. 접근성 요구.
5. **분위기**: 기존 화면과 같게 / 조금 다르게 / 새 방향. 새 방향이면 `frontend-design`의 방향 질문(주제에서 미감을 끌어내기, 템플릿 티 안 나게).

사용자만 정할 값(개수, 기간, 형식)은 지어내지 않고 질문이나 가정으로. 라운드는 보통 1~2번.

## 4. 구성 비교

같은 화면의 구성 2~3개를 표로: 이름(테이블 / 카드 / 타임라인처럼 구조를 말하는 이름, "A안" 금지), 축(무엇이 다른가), 맞는 경우, 비용. 추천 첫 번째. 카드로 고르게 한다. 라이브러리가 걸리면(차트, 명령 팔레트, 드래그, 토스트 …) `pick-ui-library`의 목록으로 고른다.

## 5. 설계 문서

`docs/design/<slug>.md`(폴더가 없으면 만든다). 한국어. 절:

```
# <화면>
## 목적과 독자       한 줄씩
## 흐름              진입 → 주 행동 → 끝. 분기가 있으면 표
## 구성              고른 구성과 이유(원칙 ID). 비교했던 대안 한 줄씩
## 요소              표: 요소 | 재사용 컴포넌트·토큰 | 새로 만드는 것과 이유
## 상태              기본·로딩·빈·오류. 빈 상태의 다음 행동 하나
## 문구              제목·버튼·오류 문구. 버튼은 동사
## 반응형·접근성     좁은 화면 배치, 포커스 순서, 색 외 표시, aria-live
## 구현 지시         마크업 구조, 테마별 확인할 것. 코드 경로는 적지 않는다
## 가정과 열린 질문
```

## 6. 끝

한 줄: 경로, 구성, 열린 질문 수. 그리고 "시안을 보려면 `/mock <요소>`, 구현은 `/dev docs/design/<slug>.md`".

## 하지 않는 것

- 코드 수정, 커밋, 시안 만들기(그건 `/mock`).
- 범위 밖 화면 재설계, 원칙 문서 직접 고치기(변경은 제안으로).
