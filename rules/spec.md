# spec 규칙

`/spec`이 따르는 절차. 넓히고(질문·선택지) → 적고 → 깎는다. 코드는 고치지 않는다. 짧은 말투(caveman)를 쓰지 않는다. spec은 사람이 읽는 문서다.

## 1. 질문 라운드

- 방식은 `grilling`(설계 결정을 나무로 보고, 지금 물을 수 있는 것을 한 라운드에 전부 묻는다). 형식은 `ask.md`(질문 카드 도구가 있으면 반드시 카드, 추천 첫 번째, 한 번에 4개까지). 첫 라운드에 범위·확인 절차·빈 상태·실패 처리처럼 사용자가 정할 것을 빠짐없이 올린다. 하나만 묻고 나머지를 혼자 정하지 않는다.
- 사실은 사용자에게 묻지 않고 직접 찾는다: 레포 구조, 기존 API, 비슷한 기능, 테스트 방식.
- 답이 다른 질문을 열면 다음 라운드. 더 물을 것이 없을 때(조용히 가정한 것이 없을 때) 끝.
- 라운드는 보통 2~3번. 5번을 넘기면 멈추고 지금까지 정해진 것으로 초안을 쓴 뒤 남은 질문을 `열린 질문`에 적는다.

## 2. 선택지

구현 방법이 둘 이상이면 2~3개를 표로: 무엇이 달라지나, 비용, 되돌릴 수 있나. 추천 첫 번째. 카드로 고르게 한다.

## 3. 초안

`to-spec`의 틀을 쓴다. 한국어. 절 이름:

```
# <제목>
## 문제          사용자 관점에서 무엇이 불편한가
## 해결          사용자 관점에서 무엇이 달라지나
## 사용자 이야기  "<누가>로서 <무엇>을 원한다, <왜>" 번호 목록. 빠짐없이
## 기능          F1, F2 … 각각 한 줄 + 서브태스크. 직군(frontend/backend/…)을 적는다
## 구현 결정      바뀌는 모듈, 인터페이스, 계약, 저장 데이터. 파일 경로·코드는 적지 않는다(금방 낡는다)
## 테스트 결정    무엇이 좋은 테스트인가(외부 동작만), 어느 모듈을, 레포의 비슷한 테스트
## 완료 조건      체크리스트
## 안 하는 것     범위 밖. 4단계에서 깎인 것도 여기
## 열린 질문      답 못 받은 것
```

## 4. 깎기

기능마다 세 질문. 하나라도 "아니오"면 `안 하는 것` 또는 `나중에`로 옮기고 이유 한 줄.

1. 꼭 있어야 하나? 요청에 없는 것은 아니다.
2. 레포에 이미 있나? 있으면 그걸 쓴다.
3. 표준 라이브러리·플랫폼 기능으로 되나? 되면 새로 안 만든다.

(ponytail이 설치돼 있으면 그 규칙이 이 셋을 더 자세히 말한다. 이 단계에서만 쓴다.)

## 5. 저장

`docs/specs/<slug>.md`에 쓴다(폴더가 없으면 만든다). 요청에 다른 경로가 있으면 그곳. slug는 영문 소문자 2~4단어. 끝에 경로와 기능 수, 열린 질문 수를 한 줄로 알린다.
